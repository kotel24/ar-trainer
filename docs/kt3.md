## 5.2 Объектно-ориентированная реализация

Объектно-ориентированная версия написана на Java 21. Исходные файлы находятся в каталоге src/java. Точка входа программы — класс Trainer. Команда demo показывает шаги сценария, а команда check проверяет действия стажёра и сохраняет результат.

Для обеих версий используется один формат CSV. В ООП-версии CsvStore преобразует строки таблиц в типизированные записи Java (record). Например, Scenario хранит данные сценария, Attempt — данные попытки, а AttemptError — номер попытки, код шага и вид ошибки.

Классы программы разделены по назначению.

1) Trainer выбирает команду по имени из Map<String, TrainerCommand>. DemoCommand и CheckCommand реализуют общий метод run интерфейса TrainerCommand. Каждый класс описывает свой режим работы.

2) CsvStore читает исходные таблицы и готовит данные для команд. Метод graph загружает шаги выбранного сценария и оставляет зависимости между этими шагами, а метод actions восстанавливает порядок действий стажёра.

3) ScenarioGraph строит порядок показа. Метод demoOrder реализует алгоритм Кана и выбирает следующий доступный шаг из очереди с приоритетом по номеру шага. Если в зависимостях есть цикл, программа сообщает об этом. Метод criticalSteps выделяет шаги, от которых зависят опасные действия.

4) AttemptChecker проверяет попытку. Метод check хранит выполненные и правильно выполненные шаги в двух множествах Set. Он передаёт проверку условий двум наследникам CheckRule. Сначала DangerousDependencyRule проверяет опасную зависимость, затем OrderRule проверяет обычное нарушение порядка. Оба правила переопределяют matches, а запись об ошибке создаёт общий метод error базового класса. Если попытка продолжается до конца, check отдельно отмечает пропущенные шаги.

5) Метод AttemptChecker.evaluate вычитает штрафы и определяет результат по баллу, затраченному времени и наличию останавливающей ошибки. CsvStore.save обновляет балл и результат в attempts.csv и заменяет строки этой попытки в errors.csv. Поэтому при повторной проверке записи об ошибках не дублируются. Коллекции и средства ООП Java описаны в [17].

Программу собирают и запускают из каталога src/java (листинг 5).

Листинг 5 – Команды сборки и запуска ООП-версии

```sh
javac -encoding UTF-8 -d out *.java
java -cp out Trainer demo data 1
java -cp out Trainer check data 2
```

## 5.3 Сопоставление реализаций

Таблица 5.1 — Сопоставление процедурной и объектно-ориентированной версий
| Элемент | Процедурная версия | ООП-версия | Причина изменения |
| Хранение сущностей | Список List хранит строки CSV, карта Map хранит поля каждой строки. | Классы-записи Scenario, Attempt и ещё семь типов хранят данные предметной области. | Типы описывают предметные данные. Числа для расчётов преобразуются из исходных полей CSV |
| Показ и алгоритм Кана | Статический метод Trainer.runDemo() выводит шаги, Trainer.buildDemoOrder() строит порядок. | Класс DemoCommand реализует интерфейс TrainerCommand и выводит шаги. Trainer выбирает реализацию TrainerCommand по имени команды. |
| Проверка и обход действий | Статический метод Trainer.checkActions() проверяет действия по порядку. | Метод AttemptChecker.check() обходит действия и применяет правила проверки. | В обеих версиях множества локальны. | Оценка и сохранение | Статический метод Trainer.evaluateAttempt() рассчитывает итог, Trainer.saveAttempt() записывает его в CSV. | Метод AttemptChecker.evaluate() рассчитывает итог, метод CsvStore.save() записывает его в CSV. | Разделение расчёта и записи сохранено. В ООП-версии за расчёт отвечает AttemptChecker, за работу с CSV — CsvStore. |
| Ошибки | Статический метод Trainer.newError() создаёт карту с данными ошибки. | Запись AttemptError хранит ошибку, запись ErrorKind описывает её вид и штраф. Метод CheckRule.error() создаёт ошибку. | Вместо карты используются типизированные записи об ошибке и её виде. Штраф в обеих версиях берётся из справочника. |
| Добавление правила | Новое условие добавляется в статический метод Trainer.checkActions(). | Новый подкласс CheckRule переопределяет метод matches(). Экземпляр подкласса добавляется в список правил. | Условие вынесено в отдельный класс, приоритет задаётся порядком правил |

В процедурной версии один файл, один класс и 17 объявленных методов, включая main. В ООП-версии 18 файлов, 19 классов и один интерфейс, а объём исходников вырос с 354 до примерно 450 строк вместе с пустыми строками. Java и стандартная библиотека общие для обеих версий. Классы, интерфейсы и record дают языковые средства для выбранной структуры. Перенос обязанностей в отдельные объекты и вызов команды через общий интерфейс относятся к парадигме.

Например, можно выделить ошибку «Шпиндель остановлен до сверления». Правилу нужны идентификатор текущего шага, признак его первого выполнения и множество правильно выполненных шагов. Оно срабатывает при первой остановке шпинделя, если сверление ещё не засчитано. В процедурной версии условие добавляется в Trainer.checkActions(). В ООП-версии в контекст проверки нужно передать эти данные, создать подкласс CheckRule и поставить его в AttemptChecker.rules после DangerousDependencyRule, перед OrderRule. Тогда при совпадении условий запишется одна ошибка с более высоким приоритетом. Код и штраф нового вида добавляются в error_kinds.csv.

Обе версии запускались с отдельными копиями одинаковых CSV. Сравнивались стандартный вывод, поток ошибок, коды завершения и содержимое attempts.csv и errors.csv. Результаты на исходных данных приведены в таблице 5.2. Полный вывод попытки 2 показан в листинге 4.

Во всех проверках использовался префикс java -cp out Trainer. Для проверки цикла в dependencies.csv добавили строку 101;104;0. Шаг 104 уже зависел от шага 101, поэтому новая зависимость замкнула цикл. После запуска demo data 1 обе версии вывели одинаковое сообщение о цикле и завершились с кодом 1.

Для проверки справочника из error_kinds.csv сначала удалили строку DANGER. На другой копии заменили stops_attempt=1 на stops_attempt=0 в строке DANGER. В каждом случае запускали check data 2. При повторном запуске check data 2 на уже сохранённых данных обе версии вернули тот же результат, а содержимое обоих файлов протокола осталось прежним.
